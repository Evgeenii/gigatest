## 1. Общая оценка зрелости

Фреймворк GigaTest демонстрирует зрелую архитектуру с чётким разделением ответственности между skills, agents и context overlays. Концепция **skills-first** внутренне согласована: skill — инструкция, agent — оболочка. **Stack-agnostic** ядро (agent-workflow-core, testing-standards) корректно изолирует стеко-специфику в оверлеях. Система двойной документации (agent-state.json + test-plan.md) — сильная сторона, обеспечивающая machine-readable source of truth при human-readable ревьюемости.

**Ключевые зоны риска:** (1) Non-deterministic выбор задач из-за фразы «или иную логику» в W1.4; (2) Протокол разрешения конфликтов test-plan.md/md основан на mtime — не криптографичен и молча перезатрёт ручные правки; (3) State Discovery (W10) не определён при наличии нескольких планов; (4) JSON-схема валидирует синтаксис, но не семантику плана; (5) Мультистек не имеет приоритизации оверлеев. Эти проблемы не блокируют текущую работу, но проявятся при масштабировании на команды и CI/CD.

## 2. Архитектурные наблюдения

### 2.1 Skills-first: заявлено vs обнаружено

**Что заявлено:**

> «Любая новая функциональность начинается с skill — не с агента, не с команды» (`IMPLEMENTATION-SPEC.md §1.1`)

**Что обнаружено:**

Все 5 agent-файлов содержат дублирующие workflow-правила (W0.3, W0.4, W0.5, W8.4), которые принадлежат `agent-workflow-core`. Agent-файлы формально следуют skills-first, но фактически несут в себе «мини-версию» workflow-core.

**Потенциальное последствие:** При изменении workflow-core нужно обновить 1 + 5 файлов. Риск рассинхронизации растёт линейно с количеством агентов.

---

### 2.2 Stack-agnostic: «протекающая» абстракция

**Что заявлено:**

> «Ядро не содержит stack-специфики. Stack-специфика — только в context/ оверлеях» (`IMPLEMENTATION-SPEC.md §1.2`)

**Что обнаружено:**

Stack Detection (W10.2) корректно определяет одиночный стек. При мультистеке (напр. React frontend + Java backend) нет алгоритма приоритизации оверлеев. W10.4 говорит «загрузи оба overlay», но не определяет:
- Что делать при конфликте правил (React R5 vs Java R5 mocking)?
- Какой overlay вызывает test-implementation при полном цикле?

**Потенциальное последствие:** На мультистек-проектах агент получит противоречивые инструкции и поведёт себя non-deterministically (выберет первый загруженный overlay).

---

### 2.3 State Discovery Protocol (W10)

**Что заявлено:**

> «Найти последний `.gigacode/plans/<task-type>-*/` по дате модификации» (W10.5)

**Что обнаружено:**

Алгоритм выбора плана при N планах в директории:
1. Берёт последний по `mtime`.
2. Не учитывает контекст пользователя (какая задача актуальна?).
3. Не проверяет `session.status` (paused vs active) до загрузки.
4. При двух планах с одинаковой датой модификации — undefined behavior.

**Потенциальное последствие:** Пользователь может начать «с середины» старого плана, не зная об этом. В CI/CD — автозапуск не того плана.

---

### 2.4 Двойная документация (W0.5 + W8.4)

**Что заявлено:**

> «Если `test-plan.md.mtime < agent-state.json.session.last_updated` → Markdown устарел» (W8.4)

**Что обнаружено:**

- mtime файловой системы — не криптографический хеш. Перезапись `agent-state.json` без изменения содержимого обновляет `session.last_updated`, но `test-plan.md` окажется «устаревшим» ложно.
- Ручная правка `test-plan.md` пользователем будет молча перезатёрта без предупреждения (кроме лог-строки).
- Нет механизма «user override» — если пользователь осознанно изменил markdown, как система это зафиксирует?

**Потенциальное последствие:** Потеря пользовательских правок; энтропия контекста при частых сохранениях.

---

### 2.5 JSON Schema: синтаксис vs семантика

**Что заявлено:**

> «JSON Schema с `additionalProperties: false` везде. Нет неявных полей» (`IMPLEMENTATION-SPEC.md §1.4`)

**Что обнаружено:**

Схема предотвращает синтаксически неверный JSON. Но не предотвращает семантически бессмысленный план:
- `plan.items` с 5 задачами, все `status: "done"`, но `progress_percent: 0` — schema-valid.
- `plan.meta.count_by_status` = {done: 999} при 3 задачах — schema-valid.
- `memory.history` с записями в обратном хронологическом порядке — schema-valid.

**Потенциальное последствие:** Агент может сгенерировать формально корректный, но логически противоречивый state. Валидация пропустит.

---

### 2.6 Гарантии воспроизводимости

**Что заявлено:**

> «Агент работает с agent-state.json, выбирает pending задачу по W1.4»

**Что обнаружено:**

Воспроизводимость зависит от:
1. Детерминизма W1.4 (первая по приоритету — но если приоритеты равны?).
2. Стабильности LLM-промтов (одинаковый вход ≠ одинаковый вывод теста).
3. Контекста `memory.context` (если knowledge накопился — повторный запуск даст другие результаты).

**Потенциальное последствие:** Два запуска «выполни следующую задачу» на неизменённом коде дадут разные тесты. Это допустимо для LLM, но не декларируется явно.

## 3. Противоречия и логические разрывы

| # | Противоречие | Где | Последствие |
|---|-------------|-----|-------------|
| C1 | W1.4: «первую по приоритету (или иную логику)» vs W2.1: «Одна задача за итерацию (STRICT)» | `agent-workflow-core` | «Или иную логику» допускает произvol — нарушает детерминизм STRICT |
| C2 | W0.3: `agent-state.json` — источник истины, но W8.4 перезаписывает `test-plan.md` без merge | `agent-workflow-core` W0.3 + W8.4 | Если юзер отредактировал test-plan.md → его правки исчезнут молча |

| C4 | testing-standards §1.3 «No Duplication» vs 4 перекрывающихся quality checklist в разных файлах | testing-standards + test-audit + test-review + overlays | Система сама дублирует то, что запрещает |

| C6 | W3.2: «агент может добавить knowledge» vs W0.2 «наблюдаемость результатов» | `agent-workflow-core` W3.2 | Если агент «не может» — knowledge не обновится, но это не наблюдаемо |

## 4. Граничные случаи (Edge Cases)

### EC-1: Два плана с одинаковой датой

**Сценарий:** Пользователь два дня подряд запускал audit. В `.gigacode/plans/` есть:
```
tests-audit-2026-04-18/
tests-audit-2026-04-19/
```
Оба имеют `session.status: "active"`. Какой выбрать?

**Ожидаемое:** Агент выбирает более новый (2026-04-19) или спрашивает пользователя.

**Текущее поведение:** W10.5 сортирует по mtime директории. Если оба созданы в один день — порядок undefined. При одинаковых именах — OS-dependent sort order.

---

### EC-2: Ручная правка test-plan.md

**Сценарий:** Пользователь вручную добавил комментарий в `test-plan.md` (например, пометил задачу «отложить»). Агент запускается, видит `mtime(test-plan.md) < session.last_updated`, перегенерирует файл из JSON.

**Ожидаемое:** Предупредить пользователя перед перезаписью. Или: поддерживать user-annotations поверх генерируемого markdown.

**Текущее поведение:** Молча перезаписывает (W8.3). Пользовательские правки теряются.

---

### EC-3: Семантически некорректный, но schema-valid state

**Сценарий:** Агент по ошибке создал:
```json
{
  "plan.items": [
    {"id": "T1", "status": "done"},
    {"id": "T2", "status": "done"}
  ],
  "plan.meta": {"total_items": 2, "done": 0, "progress_percent": 100}
}
```
`done: 0` при двух done-задачах, `progress_percent: 100` при done=0.

**Ожидаемое:** Валидация должна отловить логическую несогласованность.

**Текущее поведение:** Схема принимает — это просто числа.

---

### EC-4: Мультистек с конфликтующими правилами

**Сценарий:** React overlay R5: «Не мокать внутренние функции». Java overlay R5: «Мокать все зависимости сервиса». Файл `UserService.java` вызывается из React-компонента через API. Какой mocking-правило применить?

**Ожидаемое:** Приоритет по типу тестируемого файла (Java → Java overlay).

**Текущее поведение:** Оба overlay загружены. Какой приоритетен — не определено.

---

### EC-5: Paused сессия с частично выполненным планом

**Сценарий:** Сессия A выполнила T1, T2, остановилась на T3 (`status: "in_progress"`, `session.status: "paused"`). Пользователь запускает новую сессию B с тем же планом.

**Ожидаемое:** Сессия B находит T3 `in_progress`, решает: продолжить T3 или начать T4.

**Текущее поведение:** W1.4 выбирает pending с dependencies = done. T3 = in_progress, не выбирается. T4 может быть chosen (если dependencies OK). T3 остаётся зависшей.

---

### EC-6: Пустой проект

**Сценарий:** Пользователь запускает test-audit на пустом проекте (только package.json).

**Ожидаемое:** Чёткий ответ — «нет файлов для тестирования».

**Текущее поведение:** Аудит просканирует, найдет 0 тестов, 0 источников. Что писать в план — неясно.

## 6. Чек-лист готовности задачи

Перед тем как пометить архитектурную задачу `done`:

- [ ] Изменённые файлы прошли `grep` — нет «старых» формулировок, которые создают рассинхрон
- [ ] Если изменён `agent-workflow-core/SKILL.md` — все 5 agent-файлов обновлены (ссылки или новые правила)
- [ ] Если добавлено новое поле в JSON — обе схемы обновлены + `additionalProperties: false`
- [ ] Если изменён protocol (W10.x) — обновлён IMPLEMENTATION-SPEC.md (§12 или новый раздел)
- [ ] Создан пример валидного `agent-state.json` для новой логики (если применимо)
- [ ] `backlog.yaml` обновлён: `status: done`
- [ ] Стратегические документы обновлены (IMPLEMENTATION-SPEC.md, READINESS-MATRIX.md)
