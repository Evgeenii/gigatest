## 1. North Star

> **GigaTest — это первый skills-first тестовый workflow для AI-агентов, который делает
> верификацию кода настолько же предсказуемой и воспроизводимой, как и его написание.**

**North Star Metric:** Процент тестовых сессий, завершившихся без эскалации к человеку
(агент самостоятельно прошёл audit → impl → review → verify).

**Целевое значение:** ≥ 70% автономных сессий через 6 месяцев после production-ready.

### Почему это важно

Сегодня AI-ассистенты пишут код хорошо. Они пишут тесты плохо: без контекста, без плана,
без памяти между итерациями, без верификации результата. GigaTest — это инфраструктура,
которая превращает «написать тест» из разового действия в управляемый, итерируемый,
воспроизводимый процесс.

## 2. Контекст и происхождение

В банк введены три артефакта:

| Артефакт | Происхождение | Адаптация | Целевая аудитория |
|---|---|---|---|
| `superpowers-5.0.6` | `obra/superpowers` (оригинал) | Без форка, для фронтендеров | Frontend разработчики |
| `gigacraft-0.1.0` | Форк + адаптация superpowers | Специализированный workflow для backend | Backend разработчики |
| `gigatest-0.1.0` | **Самостоятельная разработка** | Авторский тестовый workflow | Все: front, back, QA, fullstack |

**GigaTest не является форком.** Он использует те же паттерны (skills-first, agents,
fallback commands), но добавляет то, чего нет ни в одном из них: persistable state,
double documentation, audit-first methodology, stack-agnostic architecture.

## 3. Почему два продукта, а не один

### Аргумент от когнитивной нагрузки

Гипотетический `gigacraft-0.2.0` с тестовым workflow:
- **12 агентов** (6 craft + 6 test)
- **14 skills** (7 craft + 7 test)
- **9 команд** (4 craft + 5 test)
- **Root prompt размером ~8000 токенов**

Это cognitive overload для пользователя и blast radius при изменениях.

### Аргумент от независимости

| Параметр | GigaCraft | GigaTest |
|---|---|---|
| **Домен** | Backend: создание фич | Testing: верификация любого кода |
| **Стек** | Java + Go (оверлеи) | React + Java + JS/TS + расширяемый |
| **Аудитория** | Backend-разработчики | Все: фронт, бэк, QA, fullstack |
| **Агенты** | spec, design, impl, review, verify | auditor, strategist, implementer, reviewer, verifier |
| **State** | `.gigacraft/plans/` | `.gigacode/plans/` |
| **Версионирование** | Независимое | Независимое |
| **Идентичность** | «structured backend workflow» | «universal testing workflow» |

### Аргумент от идентичности

GigaCraft = «спроектируй и реализуй правильно».
GigaTest = «верифицируй что это работает правильно».

Эти задачи не просто разные — они требуют разного mindset, разных инструментов,
разного жизненного цикла обновлений.

## 4. JTBD-разделение

### GigaCraft Jobs-to-be-Done

> *«Когда мне нужно реализовать новую фичу по требованиям,
> я хочу получить структурированный план с дизайном и имплементацией,
> чтобы не упустить архитектурные решения и не нарушить конвенции проекта.»*

Стадии: `specify → plan → implement → review → verify`

### GigaTest Jobs-to-be-Done

> *«Когда мне нужно верифицировать качество кода (своего или чужого),
> я хочу получить audit покрытия, план по написанию тестов и итеративное выполнение с проверкой,
> чтобы быть уверен что тесты реально проверяют поведение, а не замусоривают кодовую базу.»*

Стадии: `strategy → audit → implement → review → verify`

### Точка пересечения (и только она)

Оба продукта разделяют `testing-standards.md` — базовые принципы тестирования
(behavior over implementation, AAA, no duplication). Это единственная точка синхронизации.

## 5. Killer Features GigaTest

### 5.1 Persistable JSON State
`agent-state.json` — единый источник истины для сессии. Агент может прервать работу,
вернуться через день и продолжить с точного чекпоинта. Никакой потери контекста.

**Конкурентное преимущество:** Ни superpowers, ни gigacraft не имеют persistable state
для тестового workflow.

### 5.2 Double Documentation (W0.5)
Каждое изменение state → автоматическая регенерация `test-plan.md`.
Человек видит прогресс в Markdown. CI видит diff. Агент работает с JSON.

**Конкурентное преимущество:** Git-trackable progress. PR содержит не только код тестов,
но и наглядный diff плана.

### 5.3 Audit-First Workflow
Никогда не пишем тесты без аудита. Сначала — полный анализ coverage,
quality checklist, приоритизация. Только потом — имплементация.

**Конкурентное преимущество:** Устраняет главный антипаттерн AI-тестирования:
«напиши тесты для X» → агент пишет что попало без понимания контекста.

### 5.4 Stack-Agnostic с оверлеями
Ядро — универсальное. Оверлеи (React, Java, JS/TS) — детальные инструкции
для конкретного стека без загрязнения общих принципов.

**Конкурентное преимущество:** Один продукт для всей команды (фронт + бэк).

### 5.5 Quality Gate System
Каждая задача имеет явные `quality_gate` критерии. Test-reviewer кросс-проверяет
выполненные задачи против этих критериев. Нет gate → нет done.

**Конкурентное преимущество:** Встроенная система верификации качества,
а не «надеемся что тест хороший».

### 5.6 Итеративное выполнение (W2.1)
Одна задача за итерацию. Атомарные обновления state. Никогда не теряем прогресс.
Легко возобновить после прерывания.

## 6. Killer Features GigaCraft

> Краткий контекст для понимания разделения.

- **Multi-agent review pipeline** — spec → design → impl проходит через несколько специализированных агентов
- **Plan Pack с компаньонами** — структурированный план с дизайн-документом, ADR, migration guide
- **Self-review в brainstorming** — агент критикует собственные предложения до финализации плана
- **Backend-specific overlays** — Java Spring, Go, детальные паттерны для backend

## 8. Мост: interoperability, не merge

**Принцип:** GigaTest и GigaCraft — самостоятельные продукты. Мост — опциональное удобство.

### Три уровня моста (от простого к сложному)

**Уровень 1 — Awareness (минимальный)**
GigaCraft напоминает запустить `/audit-tests` после завершения реализации фичи.
Не блокирует. Не автоматизирует. Просто напоминает.

**Уровень 2 — Cross-workflow Trigger (средний)**
GigaTest умеет читать `.gigacraft/plans/*.md` и извлекать `touched_files[]`
как seed для аудита. Без GigaCraft — работает как обычно.

**Уровень 3 — Shared Standards (постоянный)**
`context/testing-standards.md` — синхронизирован между продуктами.
Это единственный разделяемый артефакт.

### Что НЕ входит в мост — никогда

- Общие агенты
- Общие skills
- Общий root prompt
- Общая версия/релиз
- Зависимости в коде
- Автоматический запуск тестов после имплементации
- Shared state между продуктами

### Приоритет

Мост — **после prod-ready GigaTest**. Не раньше.

## 9. Принципы принятия продуктовых решений

Когда возникает неоднозначный выбор, применяем эти принципы в порядке приоритета:

### P1. Workflow integrity
Целостность workflow важнее convenience features. Если фича нарушает audit-first
или атомарность итераций — она не принимается.

### P2. Explicit over implicit
Явный state в JSON лучше неявной памяти. Явный exit condition лучше «само закончится».
Явный quality gate лучше «надеюсь что хорошо».

### P3. Stack-agnostic core
Любое изменение ядра (agent-workflow-core, testing-standards) должно работать
для всех стеков. Stack-специфика идёт в оверлеи.

### P4. Completeness over velocity
Лучше меньше фич, но каждая — production-ready. Незаконченные фичи хуже отсутствующих.

### P5. Human-readable always
Любое состояние системы должно быть понятно человеку без инструментов.
`test-plan.md` всегда актуален. `agent-state.json` всегда читаем.

## 10. Anti-goals

**Навсегда:**
- Слияние GigaTest и GigaCraft в один продукт
- Общие агенты или shared skills между продуктами
- Автоматический запуск тестов (без явного запроса пользователя)
- Модификация production code агентами (только тесты)
- Зависимость GigaTest от GigaCraft для базового функционала

**До достижения production-ready:**
- CI/CD интеграция
- Мост уровней 1 и 2
- Python/Go оверлеи
- CLI-утилиты

## 11. Полный цикл разработки

```
┌─────────────────────────────────────────────────────────────────┐
│                    ПОЛНЫЙ ЦИКЛ С ДВУМЯ ПРОДУКТАМИ               │
├─────────────────────────────────────────────────────────────────┤
│  GigaCraft:                                                      │
│  specify ──→ plan ──→ implement ──→ review ──→ verify           │
│                                          │                       │
│                         [awareness: "запусти /audit-tests"]      │
│                                          │                       │
│  GigaTest:                               ↓                       │
│  strategy ──→ audit ──→ implement ──→ review ──→ verify         │
│                 ↑                                                 │
│    (seed: touched_files из GigaCraft Plans — опционально)       │
└─────────────────────────────────────────────────────────────────┘
```

### Автономный сценарий GigaTest (без GigaCraft)

```
Любой код → test-audit → agent-state.json + test-plan.md →
test-implementer (N итераций) → test-reviewer → test-verifier →
✅ Verified
```
