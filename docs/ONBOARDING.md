# ONBOARDING — Быстрый старт с GigaTest

> Версия: 1.0 | Дата: 2026-04-18
>
> **Назначение:** 4 типичных сценария работы с GigaTest — пошаговые руководства ≤ 10 шагов.
>
> **Аудитория:** Новые пользователи GigaTest.

## Сценарий A: Нет тестов совсем

**Когда:** Проект существует, но тестов нет.

| Шаг | Действие |
|-----|----------|
| 1 | Убедитесь, что `gigatest` установлен: `qwen extensions list` → должен быть в списке |
| 2 | Откройте проект в Qwen Code |
| 3 | Напишите: **«проведи аудит тестов в этом проекте»** |
| 4 | `test-auditor` просканирует проект и создаст план в `.gigacode/plans/tests-audit-YYYY-MM-DD/` |
| 5 | Откройте `test-plan.md` — список приоритизированных задач (critical → high → medium) |
| 6 | Напишите: **«выполни следующую задачу из плана»** — `test-implementer` напишет первый тест |
| 7 | Повторяйте шаг 6, пока все critical/high задачи не будут выполнены |
| 8 | Перед PR: **«проведи ревью написанных тестов»** → исправьте замечания |
| 9 | **«проверь что все тесты проходят»** → убедитесь что verification gate пройден |
| 10 | Коммитите тесты и `.gigacode/plans/` в репозиторий |

## Сценарий B: Есть плохие тесты

**Когда:** Тесты существуют, но падают, дублируются или не проверяют поведение.

| Шаг | Действие |
|-----|----------|
| 1 | Откройте проект в Qwen Code |
| 2 | Напишите: **«проведи аудит тестов в этом проекте»** |
| 3 | `test-auditor` оценит качество существующих тестов (не только наличие) и присвоит статусы: `full` / `partial` / `invalid` / `missing` |
| 4 | Откройте `test-plan.md` — задачи со статусом `partial` и `invalid` будут приоритизированы |
| 5 | Напишите: **«выполни следующую задачу из плана»** — `test-implementer` улучшит или перепишет тест |
| 6 | Повторяйте шаг 5 для всех некачественных тестов |
| 7 | Напишите: **«проведи ревью написанных тестов»** — `test-reviewer` найдёт проблемы |
| 8 | Исправьте замечания, повторите шаг 7 если нужно |
| 9 | **«проверь что все тесты проходят»** → убедитесь что verification gate пройден |

## Сценарий C: Написать тесты для новой фичи

**Когда:** Разрабатываете новую фичу и хотите сразу покрыть её тестами.

| Шаг | Действие |
|-----|----------|
| 1 | Убедитесь, что в проекте уже есть план от `test-auditor` (проверьте `.gigacode/plans/`) |
| 2 | Если плана нет — проведите аудит (см. Сценарий A, шаги 2–5) |
| 3 | Если новая фича не покрыта текущим планом, напишите: **«обнови стратегию тестирования — добавлена новая фича»** |
| 4 | `test-auditor` (или `test-strategist`) просканирует новые файлы и добавит задачи в план |
| 5 | Откройте обновлённый `test-plan.md` — новые задачи будут добавлены |
| 6 | Напишите: **«выполни следующую задачу из плана»** — тест будет написан |
| 7 | Повторяйте шаг 6 для всех задач новой фичи |
| 8 | **«проведи ревью написанных тестов»** и **«проверь что все тесты проходят»** |

## Сценарий D: Ревью тестов перед PR

**Когда:** Тесты написаны, нужно проверить качество перед отправкой на мерж.

| Шаг | Действие |
|-----|----------|
| 1 | Убедитесь, что `agent-state.json` существует в `.gigacode/plans/` |
| 2 | Напишите: **«проведи ревью написанных тестов»** |
| 3 | `test-reviewer` загрузит plan, проверит `quality_gate` для каждой задачи |
| 4 | Получите список находок с severity (critical, major, minor) |
| 5 | Исправьте critical/major замечания |
| 6 | Повторите ревью (шаг 2) если нужно |
| 7 | Напишите: **«проверь что все тесты проходят»** — `test-verifier` запустит тесты и подтвердит gate |
| 8 | Если verification прошёл — коммитите и пушьте |

## Сценарий E: Обнаружить конвенции проекта

**Когда:** В проекте уже есть тесты, и вы хотите чтобы новые тесты писались в том же стиле.

| Шаг | Действие |
|-----|----------|
| 1 | Откройте проект в Qwen Code |
| 2 | Напишите: **«найди конвенции тестирования в этом проекте»** |
| 3 | `convention-discoverer` сканирует тесты, конфиги, документацию, код |
| 4 | Получите `.gigacode/conventions/project-conventions.md` и `.json` |
| 5 | Проверьте: **«проведи ревью обнаруженных конвенций»** |
| 6 | После approve — все test-agенты пишут тесты в стиле проекта |

## FAQ

### Q: Что если `test-plan.md` рассинхронизирован с `agent-state.json`?

A: Agent автоматически перегенерирует `test-plan.md` из JSON (W8.4). Если нужно принудительно — скажите: **«обнови test-plan.md из agent-state.json»**.

### Q: Сколько времени занимает аудит проекта?

A: Зависит от размера. Для React-проекта с 20+ компонентами — обычно одна сессия (10–15 минут). Для больших проектов — `test-auditor` может разбить на несколько итераций.

### Q: Можно ли писать тесты без аудита?

A: Да, но без плана агент пишет вслепую — рискует дублировать или пропустить критичные сценарии. Рекомендуется хотя бы минимальный аудит.

### Q: Что такое `quality_gate`?

A: `quality_gate` — это список требований к качеству теста для каждой задачи. Например: «UI test с userEvent», «async проверка с await findBy*», «минимум 3 it блока». Определяется на стадии аудита.

### Q: GigaTest работает с Python/Go/другим стеком?

A: Ядро stack-agnostic. Оверлеи для React, Java, JS/TS, Python, Go — включены. Если стек не определён — используется `testing-standards.md` как fallback.

### Q: Что коммитить в репозиторий?

A: Коммитите: тестовые файлы + `test-plan.md`. Файлы `.gigacode/plans/*/agent-state.json` — это рабочие артефакты (по умолчанию в `.gitignore`). Если хотите коммитить plan для trackability — это тоже ок.

### Q: Как добавить новый стек (overlay)?

A: Создайте `context/<stack>-testing.md` с разделами R1–R7 (описано в IMPLEMENTATION-SPEC.md). Агент подключит его автоматически при определении стека по `package.json`/`pom.xml`/`go.mod`.
