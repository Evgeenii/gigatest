# gigatest

`gigatest` — это расширение для структурированного тестирования в Qwen Code. Оно предоставляет дисциплинированный workflow для аудита, написания, ревью и верификации тестов, применимый к UI (React) и Backend (Java, JS/TS) стекам через систему оверлеев.

> **Killer feature:** каждый план — это два файла (`agent-state.json` + `test-plan.md`), которые коммитятся в репозиторий. Вы видите diff плана в PR, отслеживаете прогресс, передаёте работу между агентами и сессиями без потери контекста.

## Зачем

Обычно работа с тестами: «надо бы покрыть тестами» → хаотичное написание → дубли → падающие тесты → их игнорируют.

`gigatest` решает это через 4 принципа:

1. **Аудит перед написанием** — сначала оценка покрытия, потом приоритизированный план, потом код
2. **Итеративное выполнение** — одна задача за итерацию, состояние в JSON, сессия не теряет контекст
3. **Контроль качества** — чек-листы поведения, async, edge cases встроены в каждый скилл
4. **Git-трекаемость** — `agent-state.json` + `test-plan.md` коммитятся, diff виден в PR

## 5 стадий workflow

```
Стратегия              Тесты не написаны          Тесты написаны
     │                         │                         │
     ▼                         ▼                         ▼
┌─────────────┐          ┌─────────────┐          ┌─────────────┐
│test-strategy│          │ test-audit  │─────────▶│ test-impl   │
│(что тестир.)│  цели    │ (что есть?) │  план    │ (пишем)     │
└──────┬──────┘          └─────────────┘          └──────┬──────┘
       │                                                 │
       └─────────────────────────────────────────────────┘
                                │
                                ▼
                         ┌─────────────┐     ┌─────────────┐
                         │test-verify  │◀────│test-review  │
                         │ (запуск)    │     │ (качество)  │
                         └─────────────┘     └─────────────┘
```

| Стадия | Skill | Агент | Что делает | Результат |
|--------|-------|------|-----------|----------|
| Strategy | `using-gigatest` | `test-strategist` | Определяет стратегию и тестовые цели | `agent-state.json` с целями |
| Audit | `test-audit` | `test-auditor` | Сканирует проект, оценивает покрытие и качество | `agent-state.json` + `test-plan.md` |
| Implementation | `test-implementation` | `test-implementer` | Выполняет одну задачу из плана, пишет тесты, проверяет | Тестовый файл + обновлённый план |
| Review | `test-review` | `test-reviewer` | Проверяет качество тестов против чек-листа и `quality_gate` | Список находок с severity |
| Verification | `test-verification` | `test-verifier` | Запускает тесты, проверяет что план полностью выполнен | Отчёт с доказательством |

> **Важно:** `test-verification` — это **gate** (контрольная точка). Агент `test-implementer` вызывает verification перед пометкой задачи как `done`. Для отдельной verification-сессии (или комплексной проверки) существует агент `test-verifier`, который проводит полную независимую верификацию с доказательствами.

## Как работают планы

После аудита (или стратегии) создаётся директория:

```
.gigacode/plans/tests-audit-YYYY-MM-DD/
├── agent-state.json          ← JSON Schema, источник истины
└── test-plan.md              ← человекочитаемый, git-trackable
```

| Файл | Роль |
|------|------|
| `agent-state.json` | Валидируется по `agent-state-schema.json`. LLM и агенты читают его как источник истины |
| `test-plan.md` | Регенерируется из JSON после каждого изменения. Группировка по приоритетам. Коммитите в репо — в PR виден diff плана |

### Почему оба файла?

- **JSON** — для машин: валидация по схеме, handoff между агентами, CI-проверки
- **Markdown** — для людей: читается в PR, видны изменения плана через git diff

Агент **обязан** обновлять оба файла синхронно (W0.5 — принцип двойной документации). Если `test-plan.md` рассинхронизирован — агент пересоздаёт из JSON с предупреждением.

## Stack-оверлеи

Ядро stack-agnostic. Специфичные стратегии подключаются через `context/`:

| Оверлей | Когда | Что добавляет |
|---------|-------|--------------|
| `react-testing.md` | React проект | RTL, Jest/Vitest, hooks, component classification |
| `java-testing.md` | Java/Spring Boot | JUnit 5, Mockito, @WebMvcTest, @DataJpaTest |
| `js-ts-testing.md` | Node/TS | Express, NestJS, Supertest, сервисы |
| `python-testing.md` | Python | FastAPI, Django, Flask, pytest, pytest-mock, SQLAlchemy |
| `go-testing.md` | Go | net/http, testify, httptest, gomock |
| `testing-standards.md` | Всегда (base) | Behavior-first, AAA pattern, forbidden patterns |

Агент автоматически определяет стек по ключевым файлам (`package.json`, `pom.xml`, `go.mod` и т.д.) и подключает нужный оверлей. Можно указать явно: «используй react-оверлей».

GigaTest включает CLI-утилиты для валидации и генерации без участия агента:

| Утилита | Что делает | Пример |
|---------|-----------|--------|

Обе утилиты используют `ajv` для строгой валидации. Exit code: `0` = OK, `1` = ошибка.

## Нюансы и правила

### 1. Итеративность — одна задача за раз

`test-implementer` выполняет **ровно одну задачу** из плана за вызов. Не просите «напиши все тесты» — просите «выполни следующую задачу». После каждой итерации агент обновляет `agent-state.json` и `test-plan.md`, затем останавливается.

**Правильно:** «выполни следующую задачу из плана» → агент делает одну → «продолжай» → следующая.

### 2. Не меняйте бизнес-логику для прохождения тестов

Если тест падает из-за бага в продакшн-коде — агент **фиксирует проблему в логе**, но не меняет код без разрешения. Это правило `test-implementation`: тесты проверяют поведение, не подгоняют.

### 3. «Частичное покрытие» ≠ «файл существует»

Аудит оценивает **качество** теста, а не факт наличия файла. Тест с одним `toMatchSnapshot()` и без взаимодействий получит статус `partial`, а не `full`. Это встроено в чек-лист аудита.

### 4. Запрещённые паттерны в тестах

Агент будет флажить:
- `expect(component.state).toBe(...)` — тестирование internals
- `jest.mock(internalFn)` — мокание внутренней логики
- `toMatchSnapshot()` как единственная проверка — нет верификации поведения
- `act(() => ...)` без `await` — устаревший паттерн

### 5. `test-verifier` — полноценный агент

Агент `test-verifier` создан (P1-007 ✅). Он проводит полную независимую верификацию: запускает тесты, проверяет план, собирает доказательства. Встроенная verification — это **gate**, который любой агент вызывает перед `done`. `test-verifier` — отдельная роль для комплексной проверки.

### 6. `test-plan.md` — коммить в репозиторий

Оба файла из `.gigacode/plans/tests-audit-*/` предназначены для git. `test-plan.md` даёт красивый diff в PR — ревьюеры видят что планировалось, что сделано, что осталось.

### 7. Handoff между сессиями

Потеряли контекст сессии? Просто откройте `.gigacode/plans/tests-audit-YYYY-MM-DD/agent-state.json` — там полная история, план, артефакты. Новый агент загружает файл и продолжает с последнего checkpoint.

### 8. State Discovery (W10)

При старте сессии агент автоматически ищет существующий `agent-state.json` в `.gigacode/plans/`. Если находит — продолжает. Если нет — начинает новый. При конфликте нескольких — выбирает по `last_updated`.

### 9. Ручные команды vs автоматический workflow

`gigatest` работает через skills-first (автоматическая маршрутизация). Команды (см. ниже) — fallback для явного контроля. Обычно достаточно просто описать задачу словами.

## Troubleshooting

### Скилл не загружается

**Симптом:** агент игнорирует `test-verification` или `test-plan-template`

**Причина:** Qwen Code ожидает `SKILL.md` в папке скилла. Если файл называется иначе — скилл не резолвится.

**Решение:** Проверьте что `skills/<название>/SKILL.md` существует. Файл должен иметь валидный front-matter: `name` и `description`.

### `test-plan.md` рассинхронизирован с `agent-state.json`

**Симптом:** Markdown показывает один план, JSON — другой.

**Решение:** Напишите «обнови test-plan.md из agent-state.json» — агент перегенерирует файл из JSON (W8.4).

### Агент выполняет сразу несколько задач

**Симптом:** агент пишет все тесты за раз, вместо одного.

**Причина:** Нарушен W2.1 (одна задача за итерацию). Это антипаттерн.

**Решение:** Напомните агенту: «выполняй только одну задачу за раз, обновляй состояние и останавливайся».

### Агенты не видят контекст между сессиями

**Симптом:** новый агент начинает с нуля, игнорируя предыдущую работу.

**Причина:** сессия не загружает `agent-state.json` из `.gigacode/plans/`.

**Решение:** Откройте `test-plan.md` из нужной папки — агент автоматически распознает его как продолжение существующего плана.

### `additionalProperties: false` блокирует валидацию

**Симптом:** JSON не проходит валидацию, хотя кажется корректным.

**Причина:** в JSON Schema включён строгий режим — любые поля сверх схемы запрещены.

**Решение:** Проверьте что все поля соответствуют `agent-state-schema.json`. Если нужно новое поле — сначала обновите схему, а не JSON.

### Аудит нашёл слишком много/мало задач

**Симптом:** критичных задач 20+, невозможно выполнить. Или наоборот — 1 задача.

**Решение:** `test-strategist` может пересмотреть стратегию. Напишите «пересмотри стратегию тестирования» — агент перебалансирует приоритеты, объединит мелкие задачи.

## FAQ

**Q: Зачем нужен `test-verifier` если есть verification gate?**

A: Verification gate — встроенная точка контроля, которую любой агент запускает при завершении задачи. Агент `test-verifier` (создан в Phase 1) — это отдельная роль для полной независимой верификации: запуск тест-сьюта, проверка плана, сбор доказательств. Используйте его для комплексной проверки перед мержем.

**Q: Можно писать тесты без аудита?**

A: Да. Но тогда нет плана — агент будет писать вслепую, рискуя дублировать или пропустить критичные сценарии. Рекомендуется хотя бы минимальный аудит.

**Q: Как коммитить только изменения тестов без `.gigacode/`?**

A: `.gigacode/` не должен коммититься (это рабочая директория). Коммитятся: тестовые файлы (`__tests__/`) и `test-plan.md` из `plans/` для фиксации прогресса.

**Q: GigaTest vs GigaCraft?**

A: GigaCraft — это основной workflow. GigaTest — специализированный extension для тестирования. Они используют общий стандарт (`testing-standards.md`) и могут работать вместе.

**Q: Как добавить overlay для нового стека?**
